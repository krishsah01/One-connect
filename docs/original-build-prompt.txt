## Why this exists (real failure modes to design against)

These all happened in a real multi-agent project. The product must make them impossible or loud:

**The coordinator did the work instead of coordinating.** One agent acted as lead and spent most of its usage clicking through other apps' UIs. It hit its usage limit before dispatching a ten-line fix.
**There was no shared state.** Agents worked from different, stale copies of the instructions, and nobody could see who was doing what.
**Agents sat idle.** An agent finished its task and waited for a new one instead of pulling the next queued item.
**Silent stalls.** An agent sat on an approval prompt for four days, and a headless run died on "connection timed out". No one noticed either.
**Lost evidence.** Run logs lived in a temp folder that was wiped on restart, so the handoff and test evidence were gone.
**The tracker drifted.** Work was merged while the issue still said "Todo", and bugs found along the way lived only in comments.
**Wrong models.** Agents ran on stale or weak models (a "Lite" model doing research, an old model after newer ones shipped), with no visibility.
**Usage-limit and cost surprises.** A paid fallback could have been switched on silently, and usage limits ended sessions mid-task.
**Unsafe reach.** A push to an unprotected main branch would have deployed to production immediately, and a production database had been paused for days without anyone noticing.
**Ceremony instead of progress.** Leases with expiry times, readiness "receipts" and multi-round coordination protocols consumed more effort than the work itself.
**The human was away from the desk.** The owner approves decisions from a phone, and those approvals must be quick, safe and auditable.
## Core principles

- **Bring your own subscriptions (the headline feature).** The app runs agents on the plans the user **already pays for**, so the team costs nothing extra. API keys and per-token billing are not the default.
  - Each agent runs through its vendor's **official** CLI or app, signed in with the user's own account. Examples:
    - ChatGPT Plus/Pro/Team → Codex CLI or the ChatGPT/Codex app;
    - Claude Pro/Max → Claude Code / Claude Agent SDK with the Claude login;
    - Cursor Pro → the Cursor agent CLI;
    - Google AI Pro → Antigravity and the Gemini app;
    - GitHub Copilot → Copilot CLI or agent;
    - any other vendor CLI with a login.
  - The control center **never sees, stores or proxies the user's credentials**. It calls the vendor tool, which handles its own auth (OAuth/device login). It only reports login state: logged in, expired, needs re-auth.
  - **Show each subscription's included usage:** remaining or limit status where the vendor exposes it, otherwise "unknown". Detect usage-limit errors, and route work to an agent whose subscription still has capacity.
  - **Paid modes stay off.** That covers API-key mode, on-demand or overage billing, purchased credits and auto-recharge. Turning one on requires an explicit per-agent opt-in with a cost banner.
  - **Stay within each vendor's terms:**
    - one user's subscriptions are used only by that user, never shared or pooled across users, and never resold;
    - no scraping or extracting session tokens from apps;
    - no circumventing rate limits.
    The README must tell users to check their own plan's terms for automated use.
- **Pull, not push.** Agents fetch their next work from one source of truth; the coordinator never needs to drive another app's UI. UI automation exists only as an optional, clearly labelled fallback adapter.
- **One source of truth per concern.**
  - The work tracker owns issues and statuses.
  - Git owns code.
  - The control center's event store owns runs, handoffs and decisions.
  - Everything else is a view.
- **No issue, no dispatch.** Every run is tied to a work item. Status changes happen atomically with the action that causes them.
- **Now + Next for every agent.** When an agent finishes Now, it starts Next automatically. The queue refills itself, and idle time is shown as a metric.
- **Evidence over claims.** "Done" requires recorded evidence: commands, results, SHAs. The UI never shows a step as passed without proof attached.
- **The human decides product, cost, security and deploys.** Everything irreversible or outward-facing needs per-action approval.
- **Lean process.** Leases, receipts and similar ceremony are replaced by ownership (issue ↔ agent) plus live process state.

## Domain model (implement as typed entities)

- **Project:**
  - repo path(s);
  - integration branch;
  - protected branches;
  - test, lint and build commands;
  - tracker binding;
  - release gates;
  - policies.
- **Agent:**
  - id, display name, vendor, surface (CLI, desktop app, web app, IDE);
  - role (lead/coordinator, engineer, reviewer, QA, researcher);
  - adapter type;
  - model inventory (allowed models, current model, newest available, effort level);
  - capabilities: can it write code, run shell, reach the tracker, read local files, run headless;
  - cost plan (included subscription vs metered; paid fallback must be OFF);
  - concurrency limit;
  - status.
- **Work item:** a mirror of a tracker issue. Holds id, title, description, acceptance criteria, labels, priority, parent and blocking relations, status, owner agent, linked branches/PRs/runs, and an evidence list.
- **Assignment:** work item → agent, with:
  - scope;
  - allowed paths;
  - worktree and branch;
  - base SHA;
  - required checks;
  - the handoff format;
  - Now or Next position.
  The assignment text is generated from a template and editable before dispatch.
- **Run:** one agent session. Holds:
  - process or session id;
  - model and effort;
  - start and end time;
  - state (queued, starting, running, waiting-for-approval, waiting-for-input, stalled, failed, finished);
  - a durable transcript (stream of structured events);
  - usage consumed;
  - exit reason.
- **Event:** a typed, timestamped record, for example:
  - message, tool call, file edit, command run;
  - test result (counts);
  - commit, handoff, status change;
  - approval request, error, usage warning.
- **Handoff:** a structured block parsed from the agent's final message, commit body or tracker comment:
  - Done;
  - Evidence (commands and actual results);
  - Commit (SHA and branch);
  - Blocked (what, and on whom);
  - Next.
- **Review:** reviewer agent or human, target SHA, findings, verdict. Rule: the author can never be the sole reviewer.
- **Merge:** source branch → integration branch, result, post-merge checks.
- **Release:** an ordered plan of steps. Each step has an owner, an exact command or action, a verification check, a rollback and an approval state.
- **Decision:** a question for the human, with options, a recommendation, evidence links, an urgency, and the answer with timestamp and channel. The answer is an auditable record.
- **Policy:**
  - zero extra spend;
  - model quality floor and the newest-model rule;
  - allowed and denied models;
  - approval-required actions;
  - path scopes;
  - privacy rules;
  - quiet hours.

## Adapters (all pluggable, all project-agnostic)

**1. Agent runtime adapters.** Each implements one interface: start, send, stream, pause, resume, stop, status, list_models, usage, auth_status, billing_mode, and pending_approvals.
- **Subscription-first:** every adapter defaults to the vendor's subscription login.
  - auth_status reports logged in, expired or not installed, and gives the vendor's own login command to fix it. The UI shows it as "Run <vendor login> in a terminal" or "Open the app and sign in".
  - billing_mode must report subscription / metered / unknown. Dispatch is blocked when it isn't subscription and the user hasn't opted in for that agent.
- **Onboarding wizard:** detect installed vendor CLIs and apps, check each one's login state, list its models, and let the user map each subscription to an agent role.
- **Don't bundle vendor binaries.** Users install the official tools themselves; the wizard links to each vendor's install page.
- **Pin the exact binary.** Some apps ship a newer bundled CLI than the one on the PATH, and only the newer one can run the newest models.
- **Headless CLI adapters** (preferred). Spawn the agent's own CLI inside the assignment's worktree and capture stdout and stderr as events. Examples to support out of the box:
  - an OpenAI Codex CLI (exec mode);
  - Cursor's agent CLI (print mode);
  - Claude Code / Claude Agent SDK (headless);
  - any generic "command + prompt" CLI.
  Discover each CLI's model list at dispatch time and pick the newest allowed model at the configured effort. Detect the common failure modes: unsupported model for the account, auth expired, connection/routing timeout, usage limit reached, sandbox write denied (for example, the agent can't write the git index).
- **App-bound adapters** for agents with no CLI, like desktop IDE agents and chat apps.
  - **Relay mode** (default): the control center generates a short, self-contained prompt, the human or a phone shortcut pastes it in, and the agent's result is pulled back via a shared link, a file the agent writes, or a paste box.
  - **Optional OS-automation mode:** opt-in, scoped per app, never reads unrelated chats, and every action is logged.
- **Subagent adapter:** for a lead agent that can spawn sub-workers, track them as child runs under the parent.

**2. Work-tracker adapters:** Linear, GitHub Issues/Projects and Jira, with two-way sync via webhooks plus polling fallback. Map statuses to the lifecycle below. Create issues for new findings in one click (or automatically, with a rule), and post handoffs as comments.

**3. VCS adapter:** git worktrees, one per assignment.
- Branch naming: <agent>/<issue-key>-<slug>.
- Detect file-system changes live.
- Show the diff against base.
- Enforce allowed paths with a pre-commit check and a dashboard warning.
- Detect conflicts with other active worktrees early.

**4. Code host and CI adapter:** GitHub/GitLab PRs, checks and branch protection status. Warn loudly if the production branch is unprotected.

**5. Infra status adapters (read-only by default):** hosting (for example Vercel), databases (for example Supabase/Postgres) and workers.
- Surface health such as a paused or inactive database, recent runtime errors, the migrations applied vs in the repo (including drift detection), and env-flag state.
- Any write action requires an explicit per-step approval.

**6. Knowledge adapter:** a markdown docs folder or Obsidian vault for the team contract, the brief, and decision records.

**7. Notification adapter:** mobile push or web push, plus optional chat-app delivery. No email unless explicitly enabled.

## Lifecycle (one state machine shared by all views)

Backlog → Selected → Assigned (Next) → Assigned (Now) → Running → Handoff received → In review → Changes requested ↺ → Approved → Merged to integration → Release candidate → Deployed → Verified (Done)

Side states: Blocked (on human / on issue / on agent), Stalled, Failed, Canceled.

Rules:
- Every transition writes an event and syncs to the tracker in the same operation.
- **Done** requires merge evidence AND acceptance evidence. If acceptance needs production or real-device verification, the item stays open until that evidence exists.

## Real-time architecture

- **Local supervisor daemon** on the developer's machine:
  - spawns and attaches to agent processes;
  - writes **durable** logs in an app data directory, never temp;
  - parses output into events;
  - watches worktrees;
  - receives tracker and CI webhooks, with polling as a fallback;
  - runs the rules engine.
- **Event bus:** a persistent store (SQLite by default, Postgres optional) with an append-only event log, plus WebSocket/SSE fan-out to clients.
- **Web UI:** responsive, works as a PWA on the phone. Remote access goes over an authenticated secure tunnel. No public endpoints without auth.
- **Restart-safe:** on restart, reattach to live processes or mark them orphaned, and replay state from the event log.

## Rules engine (built-in automations, each toggleable)

- **Auto-refill:** when Now finishes, promote Next and dispatch it if the policy allows.
- **Stall detection:** no new event for N minutes, or a pending approval older than M minutes → alert and surface it in Mission Control.
- **Connectivity and usage-limit handling:**
  - detect the failure;
  - check connectivity;
  - retry once;
  - then pause and suggest reassigning to another agent with capacity.
  - Never silently downgrade the model or enable paid usage.
- **Tracker reconciliation:** merged-but-not-updated, in-progress-without-a-live-run, or a finding without an issue → fix it, or ask.
- **Handoff enforcement:** a run that ends without a handoff block is flagged, and a handoff skeleton is generated from its events.
- **Newest-model check** at every dispatch.
- **Coordinator-only mode:** the lead agent can be restricted to coordination (no code-writing runs) to save its usage.
- **Infra watch:** a database paused or inactive, CI failing on the integration branch, unprotected production branch → alert.

## Safety and guardrails (non-negotiable)

- **Zero extra spend by default:**
  - included subscription usage only;
  - API-key or metered adapters must be explicitly enabled per agent, with a visible cost banner;
  - paid fallbacks stay off.
- **Secrets:** never put them in prompts, logs or tracker comments. Redact them in the event pipeline (patterns plus a configured denylist).
- **No push** to protected or production branches. **No deploys, production database writes, migrations, publishing or outbound messages** without a per-action human approval recorded as a Decision.
- **Path-scope enforcement** per assignment, and **one writer per worktree.**
- **Privacy:** never read the human's unrelated chats, tabs or files. The OS-automation adapter is scoped per app and is opt-in.
- **Audit log** of every action by every agent and by the control center itself.
- **Kill switch:** stop all runs instantly.

## Core architecture decisions

1. **Event-sourced state.** Every command handler follows the same steps:
   1. Validate the command against the in-memory state.
   2. Emit typed events.
   3. Append the events, plus any tracker-sync outbox rows, in **one SQLite transaction**.
   4. Apply them through the shared `core/reducer.ts`.
   5. Broadcast them.

   The daemon and the UI run the **same reducer**, so views can't disagree. On boot the daemon replays the log, using a snapshot plus the tail. Every event carries `actor` (agent, human or system), so the event log is also the audit log.
2. **Transcript vs control events.** Both live in one table. Control events (lifecycle, runs, agents, alerts) are broadcast to every client. Transcript events (messages, tool calls, edits, commands) go only to Agent Consoles subscribed to that run, replayed from `since=seq`.
3. **Durable, restart-safe runs.**
   - The data dir is `~/Library/Application Support/AgentControlCenter` (XDG on Linux), overridable with `ACC_DATA_DIR`. The daemon refuses to start if the data dir resolves under `os.tmpdir()`.
   - Each run gets a detached `runner` process. It spawns the vendor CLI in its own process group, **redacts every line before it touches disk**, and writes `runs/<id>/stdout.jsonl`, `stderr.log` and `exit.json`. It forwards `inbox.jsonl` to the child's stdin when the vendor supports streaming input.
   - The daemon tails these files from a stored byte offset. After a daemon restart it re-tails live runners, checking PID plus start time to guard against PID reuse. Runs that died while the daemon was down become `orphaned`, with their exit code recovered.
4. **One shared state for agents (pull, not push).** Every run gets the `acc` MCP server, which authenticates over a unix socket with a per-run token. Its tools:
   - `get_assignment`: always the current text.
   - `post_handoff`.
   - `report_finding`: creates a tracker issue (rule-gated). This stops bugs from living only in comments.
   - `ask_human`: a blocking decision or approval, which sets the run to `waiting-for-approval`.
   - `permission_prompt`: wired to Claude's `--permission-prompt-tool`.

   Claude runs use `--strict-mcp-config`, so agents **don't inherit your personal MCP servers** (Gmail, Calendar and so on). This is the privacy rule.
5. **Tracker sync = transactional outbox.** A lifecycle event and its tracker write are committed together. A worker delivers the write with retries, and an undelivered or failed sync raises a loud "tracker out of sync" alert. Polling ingests changes made directly in the tracker. Webhooks need a public tunnel, so they wait for P2/P3 and your approval.
