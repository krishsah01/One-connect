# One Answer

One Answer joins committed code, project docs, design contracts, team notes, and the Graphify code graph. Human queries and authenticated agent tools use the same scoped local retrieval. It supplies cited context; it cannot guarantee an answer to every question or override a human decision.

## Intake and freshness

Opening a configured local repository starts background intake automatically. Intake resolves the integration branch to an exact commit; it uses HEAD if that branch does not exist. It reads Git blobs without a checkout, network fetch, project command, dependency install or hook. Uncommitted and untracked work is deliberately excluded and labelled in the UI. A repository without a commit shows an error. Projects added from **Projects** in the Mac app (local folder or approved clone) start the same intake as soon as their engine starts; the add screen shows the revision that will be indexed and which changes are excluded, and the project list shows each running project's own intake status. A folder without Git or without commits gets an explicit onboarding step (approved `git init`, then a first commit in the project terminal) instead of an index. Indexing of separate active assignment revisions remains subsequent work.

Supported source, documentation, manifest and Docker/config files are extracted into a bounded snapshot. Symlinks, submodules, hidden private folders, credential/env files, certificates, binary files, generated/vendor trees and lockfiles are excluded. Limits are 500 files, 64 KiB per file and 5 MiB total. The dashboard shows included/tracked/excluded counts and marks size-limited results partial. Node package names, dependencies and scripts are extracted declaratively; scripts are never presented as passing tests.

Redaction happens before note, embedding or graph storage, including source paths, manifest names, dependency names, script keys and values, and JSON-escaped strings. Ordinary source paths are retained; changed or oversized path components receive stable opaque aliases with their language extension. Aliases separate paths whose secret values redact alike and never use redactor output as a filesystem path. Source paths are bounded to 4096 bytes. Citations expose the safe snapshot path, exact revision and redacted content hash. Selected user notes with secret-bearing paths use an in-memory path lookup; their index and citations contain only safe aliases, and the citation's URL is empty rather than revealing the original path or a sensitive vault name.

Generated notes use a project-owned collection and atomic replacement; intake refuses to overwrite an unowned directory or a new generated filename colliding with an unregistered user note. Unknown additions are preserved without reading their bodies and excluded from generated-source retrieval. Missing, edited or symlink-replaced registered notes and changed overviews invalidate the cache and are regenerated safely. Source content stays inside fenced Markdown, including content containing its own fences. A private per-project Markdown vault is provided until the user selects an Obsidian vault. Existing unrelated vault notes are never read.

The managed namespace is `<knowledge.folder>/project-<SHA-256 of canonical project.repo>`. Display-name changes and repository symlink aliases retain the namespace; two different repositories with the same name remain isolated in a shared vault. Ownership markers bind the folder and generated registry to that identity. Explicit shared context folders remain supported, but selections overlapping the managed parent and other owners' marked folders grant no access. Project scopes use local traversal rather than vault-wide Obsidian CLI search, excluding other owners before reading note bodies. The native registry must continue validating the exact canonical repository binding and giving each project its own daemon data directory; its configuration-path ID and this repository-bound note identity have different representations.

Legacy display-name folders and the old generic generated marker do not prove project identity. Migration regenerates source notes from the exact committed snapshot in the new namespace, rewrites the daemon-owned attribution registry, and rebuilds the scoped document index. Contract, brief, issue, handoff and decision notes are regenerated from persisted project state. Legacy folders, including previously generated sources and user/foreign additions, are left untouched and are never included in retrieval or read to verify migration. Their old wikilinks are not automatically redirected. This also handles a shared legacy folder last written by another same-name project without adopting that project's content.

Graphify receives this same redacted snapshot, rather than the live worktree. Its AST extraction invokes no LLM. Graphify must be installed by the user; the app never installs it automatically. Semantic retrieval likewise requires an already-installed local Ollama embedding model and an explicit local search setting. Missing tools/models leave keyword retrieval working and show partial status. Notes, vectors and graph revisions are shown individually; ready requires all configured pipeline stages and no source truncation.

Intake checks for integration changes every minute when graph auto-update is enabled. Re-index project forces a refresh. Generated source integrity and the redaction denylist identity invalidate the cache. Deleted/replaced sources are removed from the retrieval index. Source-line attribution is derived from a daemon-owned registry, current scoped excerpts and content hashes; arbitrary note frontmatter, forged excerpts and cached excerpts from older content cannot claim the latest commit. Notes, embeddings and Graphify consume the same redacted snapshot. A missing model after restart remains partial even if old vectors exist. Settings, attribution and progress persist; interrupted intake resumes on restart. Shutdown cancels local model and Graphify requests.

## Agent tools and evidence

`search_context` returns bounded source snippets and optional graph context. `ask_project` returns the same excerpts or local-model interpretation as the dashboard, with citations and intake status. `read_note` provides redacted pages. These sources are untrusted task context, not permission to execute a command or expand scope.

`packages/daemon/test/one-answer.test.ts` covers exact commit extraction versus dirty files; source exclusions/redaction; input validation; count/size bounds; automatic note/vector/graph sync; revision changes; removal of stale passages; authenticated dashboard queries; citation integrity; and restart recovery. Its embedding and Graphify fixtures prove integration behavior, not model quality. The separate real-model retrieval benchmark is documented in [Ask your docs](ask-your-docs.md).

`packages/daemon/test/context-isolation.test.ts` covers same-name projects sharing a vault, independent restarts and revisions, rename stability, legacy migration without reading legacy bodies, ownership and symlink boundaries, user-note preservation, note/overview repair, stale and forged citations, escaped manifest metadata, bounded source aliases and missing-model restart status. `packages/daemon/test/one-answer.strip.test.mjs` runs directly with Node 24 `--experimental-strip-types --test`, exercising the daemon, SQLite, local embedding/Graphify fixtures and restarted citations without Vitest transpilation. Live Graphify tests in `context.test.ts` require the explicit `ONE_CONNECT_LIVE_GRAPHIFY=1` opt-in.
